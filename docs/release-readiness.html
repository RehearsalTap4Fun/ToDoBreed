孵化器发布评估

现状：一个只在作者机器上跑得起来的成熟原型。机制闭环完整，工程质量尚可，但发布形态、依赖耦合和形象方向三件事挡在"别人能用"前面。

结论先行
  1. 机制层已经是产品。周循环、揭露、畸变与变异、休眠棚、图鉴、驻场、连击、模版、存档导入导出全部落地并有测试覆盖，作者本人已日常使用两周。
  2. 三个硬障碍。形象方向仍在换轨中，现有形象正是用户提出"带入不进去"的那套；运行依赖作者机器上的姊妹仓库和 181 MB 未发布的部件资源；单机启动器要求 Node 与命令行。任何一个不解决都发不出去。
  3. 建议形态是静态网站。一个链接，浏览器打开就玩，存档留在本地浏览器。单机 HTML 保留为离线备用。分三步走：两周内小圈子 Alpha，形象定稿后公开 Beta，再谈 v1。

§02

发布形态

三种可选，推荐静态网站。选它的理由是用户成本最低，且现有代码只需去掉单文件插件和姊妹目录依赖。

形态用户怎么用要做的事取舍
静态网站 推荐打开一个链接，浏览器里玩，存档留在本地改为多文件构建；部件资源随站点发布（只发 WebP，54 MB）或放对象存储；CI 自动部署到 Cloudflare Pages 或 GitHub Pages需要托管与域名；离线不可用，可后补 Service Worker
单文件 HTML下载一个文件双击已有，但 gen2 形象需要 HTTP 同源资源，file:// 下只剩古典轨只有等形象转为 SVG 扁平轨后才成立；作为离线备用保留
桌面应用下载安装包Tauri 打包，内置资源与本地服务签名、公证、三平台构建，成本最高；v1 之后再议

§05

风险与决策点

  • 画风二选一，不要并行。位图走 Codex 加 QMonster 管线，扁平走 SVG 加古典轨。两条都做等于两套部件库、两套渲染器长期维护。建议以 Codex 这轮坐姿猫的结果定夺：像就走位图，不像再回扁平。
  • 存档是唯一的用户资产。发布后任何目录版本升级都不能让旧生物消失，现有 catalogVersion 锁定机制要保住；清缓存丢档要有提醒兜底。
  • RandomPet 仓库不适合直接公开。近 1 GB 的 git 包、v0.1 和 v0.2 的废弃资源都在里面。发布时只发 v0.4.0 的 WebP，仓库本身留私有。
  • 采集器是作者专属能力。依赖本机的 AI CLI 与 Jira，别人拿到也用不了。发布版本里它必须是可选项，否则会成为最主要的"为什么不工作"来源。
  • 一个人的产品，先小后大。Alpha 五到十人足够看清第一颗蛋前的流失。公开前不需要账号系统。
